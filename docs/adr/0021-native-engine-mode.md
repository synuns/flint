# ADR-0021: 네이티브 엔진 모드 — 배치 3종·서비스 등록·전환

- **상태**: 채택 (2026-11-24, v1.31.0)
- **배경**: 엔진은 관리형 컨테이너(내장 compose — ADR-0020)와 외부
  모드(`--engine-url`, 루프백 한정) 두 가지였다. 컨테이너 런타임은
  설치 요구량이 크고 점유(디스크·메모리)가 운영 기기에서 부담이었다.
  v1.30.0 M4 네이티브 L0 스파이크(docs/plans/native-spike-v1300.md)가
  핀 바이너리의 기동·CRUD·합성 벤치·무결성을 실증해 단일 바이너리
  경로의 착수 조건이 충족됐다.
- **결정**:
  - 엔진 실행 위치를 **배치 모드 3종 단일 인터페이스**로 다룬다:
    `managed-container`(내장 compose)·`native`(플랫폼 서비스로 등록된
    flint 관리 바이너리)·`external`(운영자 자체 엔진 — 안내만).
    모드는 config `engine.mode`에 기록하고, `flint engine
    status|start|stop`은 모드×명령 행렬로 동작한다(미정의 조합은
    거부+안내).
  - **네이티브는 옵트인**이다(사용자 결정 2026-11-23). 새 설치 기본은
    관리형 컨테이너를 유지하고, 기본 전환은 무장애 운용·doctor 경고 0
    관측 뒤 별도 결정으로 남긴다.
  - **전용 다운로더**: 핀 버전·플랫폼별 해시 상수(flint 릴리스 서명이
    신뢰 뿌리 — 4방 동치 가드에 네이티브 핀 추가)로 검증한다. 중첩
    tarball에서 `bin/doltgres`를 선택해 해시·`-version` 검증 후
    `engine/<version>/`에 원자 교체하고 `current` 심링크가 가리킨다.
    구버전 디렉터리는 보존한다(롤백 원천).
  - **서비스 등록**: macOS는 launchd(plist 0600·비밀 미포함), Linux는
    systemd user 유닛 — 로그 순환은 플랫폼 사실(journald)에 맡긴다.
    서비스 관리자 부재 환경은 지원하지 않고 doctor fail+안내로
    마무리한다(수동 데몬화 표면을 만들지 않는다).
  - **자격증명**: 첫 기동에 슈퍼유저로 대상 사용자를 ALTER ROLE 하고
    ADR-0010 기본 DSN으로 재접속을 확인한 뒤 모드를 기록한다(실패 시
    미기록·정지). 기본 비밀번호 유지는 사용자 결정 — 루프백 한정 전제.
  - **모드 전환**은 container→native 단방향: 정지 → 데이터 디렉터리
    복사(0700) → 네이티브 기동 → dolt_log 깊이·AS OF 동치 확인 →
    실패 시 원복. 컨테이너 볼륨 삭제는 네이티브에서 backup+drill을
    마친 뒤 사람 운영자만(역방향 전환은 비목표).
- **근거**: 배치 3종을 단일 인터페이스로 두면 커맨드 표면(engine
  status|start|stop)이 모드와 무관해지고, doctor·전환·업그레이드 절차가
  모드별 분기 없이 재사용된다. 다운로더의 이중 검증(해시+버전)은
  핀 체인을 컨테이너 경로와 동일한 신뢰 사슬로 유지한다. 데이터
  디렉터리 복사 전환은 이력을 잃는 백업·복원보다 우수하다(스파이크는
  전환을 실증하지 않았다 — v1.31.0 e2e로 실증, 미실증 시 백업·복원
  안으로 되올린다).
- **단점**: 플랫폼별 서비스 등록(launchd·systemd) 관리 면이 늘고,
  네이티브 핀·해시 상수가 릴리스 유지 비용에 추가된다. 역방향 전환
  미지원은 네이티브 선택이 되돌리기 어려운 판정이 될 수 있다(볼륨은
  전환 전 스냅숏으로 잔존 — 사람 운영자 정리).
