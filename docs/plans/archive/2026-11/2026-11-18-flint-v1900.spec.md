# flint v1.9.0 스펙 — 다중 기기 안정화: recall append-only (스키마 v12)

## 배경

R38이 실측한 치명 2건은 업스트림(Doltgres 엔진) 제약으로 확인됐다:
양측 working set에 read 페이로드(recall bump UPDATE)가 있으면 pull 병합이
엔진 패닉(XX000)하거나, 동일 knowledge 행 read 충돌의 merge 회복이
불능한다. v1.7.2는 완화(안내·reset 회복)만 제공 — sync는 단일 활성
기기+백업/기기 이동에 한정됐다.

근본 처방: **회상 강화를 행 갱신(UPDATE)에서 append-only 이벤트로
전환**해 knowledge 행을 쓰기 경로 전용으로 되돌린다. read 페이로드가
병합 충돌 표면에서 완전 퇴장하면 이중 커밋 이벤트는 union으로 자연
병합된다.

## 필수 요구사항

1. **스키마 v12 — recall_events**: 전용 append-only 테이블
   `recall_events(knowledge_id int NOT NULL, recalled_at timestamptz
   NOT NULL DEFAULT now())` + 인덱스 (knowledge_id, recalled_at DESC).
   계측 테이블 read_events와 원천 분리(telemetry 커밋과 무관하게
   회상 원천 유지 — v1.7.0 감사/telemetry 분리 원칙 승계).
2. **EnsureSchemaV12 무손실 승격**: v11 DB에서 ① recall_events 생성
   ② 백필 — knowledge.recall_score>0 행마다 score수의 합성 이벤트를
   last_recalled_at(NULL이면 마이그레이션 시각)에 INSERT(랭킹 연속성
   보존, 합성임이 주석·HISTORY에 명시) ③ recall_score·last_recalled_at
   폐기(DROP — Doltgres DROP COLUMN IF EXISTS 미지원 주의, 가드).
3. **강화 경로 전환**: BumpRecallScores 구현을
   `INSERT INTO recall_events` 배치로 교체 — wire.RecallBumper
   시그니처·read 완료 감사 커밋("read: recall bump")·telemetry
   분리 커밋 계약 불변.
4. **파생 조회**: EffectiveRecallScore를 이벤트에서 파생 —
   raw=count(events), effective=max(0, count − decay_rate×경과일수)
   (v11 산식 동일, 하한 0·미회상 0 유지). hot/brief 랭킹·status
   카운트·tuning decay_rate 오버라이드 전부 파생 경로로. 성능은
   docs/PERF.md 관례(격리 DB·합성·3회 중앙값)로 전후 비교 기록.
5. **maintain --decay-audit 전환**: 감사 리포트가 파생 값 기준으로
   동일 서식 유지(승인제 그대로).
6. **이중 기기 회귀(수용 기준)**: 격리 DB 2개로 R38 치명 시나리오
   재현 — 양측 독립 read+쓰기 후 push/pull이 패닉 없이 성공·양측
   이벤트 union·회상 랭킹 일치. 이 실측이 green이어야 발행.
7. **문서**: HISTORY·계약행 TestVersion0190Milestone·README 배지·
   RUNBOOK"sync 다중 기기 지원"갱신·release-gate green.
