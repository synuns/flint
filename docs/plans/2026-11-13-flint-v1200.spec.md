# flint v1.2.0 스펙 — 관측 고도화: 저장 수선·계측 확장·규칙 진단

- 날짜: 2026-11-13. 사용자 구성 승인(E 패킷은 defer·별도 판단 대기).
- 원칙: additive 스키마·개인정보 무수집(카운터·바이트만)·동작·출력 불변
  (신규 필드·키는 additive)·thresholds SSOT(하드코딩 금지).
- 근거: 스키마 감사(8건)·데이터 갭 감사(12건)·레퍼런스 조사
  (CRAG·dedup 공식·Mem0·MemGPT·Duolingo HLR)·로컬 실증(G4 hot
  미계상·dup 루프 패턴).

## 1. 저장 기반 수선 (제1계층)

### 1.1 daily 플랫 키 전환
- 현황: `daily:<date>` JSON 카운터가 읽기-수정-쓰기(last-write-wins
  경합 수용·40001 재시기) — `lib/db/usage.go` bumpDaily.
- 수정: `daily:<kind>:<date>` 정수 값 플랫 키로 전환 — bumpMeta 단일
  문장 원자 증분(경합 손실·재시기 제거). 마이그레이션: 구 JSON 키는
  읽기 폴백으로만 승계(기존 창 통계 손실 방지)·신규 기록은 플랫 키.
  PruneDaily는 양쪽 키 정리. 보존 14일 불볕.
### 1.2 스키마 v10 (additive)
- read_events 신규 열: `bytes`(int·출력 바이트), `zero_reason`
  ('unowned'|'owned_miss'|'' — CRAG 3분류의 적용판·zero=1인 행만),
  `source`('hook'|'cli'|'mcp' — 채널 믹스 관측).
- 신규 테이블 `knowledge_reads(knowledge_id int, ts timestamptz,
  session text, kind 'hot'|'read')` — 항목별 회상 이력. 보존:
  read_events와 동일 창(초기 14일·thresholds `knowledge_reads_retention_days`
  분리 키). write 경로(read_count·last_read_at)는 유지(파생 캐시로
  격하 — 호환·성능).
### 1.3 잔여 수습
- hot 헤드라인(비 --full) 주입도 knowledge_reads에 kind='hot' 기록
  (주입 id 전수 — G4 계상 원천). hot_events --full 계약 불볕.
- hot_stats meta blob 폐지 — hot bytes는 hot_events/knowledge_reads
  파생(스키마 감사 2번 수습).
- 버그 즉치: `last_brief_at`을 metaKnownKeys에 등록(meta-audit
  unknown 오탐 해소).

## 2. 계측 확장 (제2계층)

### 2.1 G4 정합 — hot 회상 계상
- recall_led_pct가 knowledge_reads(kind 불문)의 세션 배정으로 산출 —
  hot-led 세션이 회상 선도로 계상(설계 결함 수선·로컬 실증).
- hot→read 연썄(갭8): 주입 후 30분 내 read 페어 `hot_read_chain_pct`
  파생(조인만).

### 2.2 제로히트 분해 (CRAG)
- zero read 시점 판정: active 지식 수 임계로 unowned(사실상 미보유)
  vs owned_miss(보유탐색실패) — daily 카운터 2종 + report
  `zero_unowned_pct`·`zero_owned_miss_pct`. 임계는 thresholds
  (`zero_owned_floor`, 기본 1 — active≥1이면 owned_miss).
  개인정보: 쿼리 본문 미기록(원칙 유지).

### 2.3 토큰 회계 완결
- read_events.bytes → `bytes_p95`(표면별·Mem0 삼중 보고 승계).
- **절약 하한** `savings_lower_bound_bytes` = Σdup × 평균 기록 바이트
  (dedup 논리-물리 공식 — 결정적 counterfactual·라벨 "하한").
- hit 원가 = Σhit × 평균 요약 바이트 — 라벨 "주입 원가"(절약 주장
  아님·조사 결론 준수). report effect에 `cost` 객체로 통합(
  bytes·p95·savings·hit_cost — always-on(hot)과 on-invoke
  (read/brief) 구분 표기).
- bytes 토큰 환산 금지 조항 유지(METRICS §5).

### 2.4 검수 결과 카운터 (갭1)
- approve(승격·not_found·supersede 오류)·maintain(supersede·
  expire-pending 확정·prune 삭제 행수·merge)·import(적립·skip)
  결과 daily 카운터 + report `curation` 객체. RecordUsageCount kind
  확장 또는 전용 카운터 키.

### 2.5 발화 카운터 (갭3·4·5)
- 넛지 발화(distill·recall·갱신 안내 각 1)·done stale 경고·
  doctor 경고 종류별 발생 수 — meta 누적 카운터(`fired_*`).
  진단 D의 원천. 개인정보 무관(횟수만).

### 2.6 회상 운명 (F)
- knowledge_reads 조인: 창 내 회상된 지식의 7일 후 운명 →
  `survived_pct`·`bad_recall_pct`(superseded/invalidated 비율).
  Graphiti 미해결 영역의 flint 선점 정의(METRICS 등급 Tier 2).

## 3. 규칙 진단 (제3계층 D)

- report `--diag`(기본 포함?) 말미 `diagnosis` 배열 — 각 문장:
  신호+수치+기준 출처+행동 1줄. **정상 침묵 유효**(문제 없으면 빈 배열).
- 기준 3계층: A 자기참조(hot avg_bytes/hot_budget ≥0.8·≤0.2·추세
  ±50%·hit/zero 원가 비교)·B 레지스트리 승계 읽기(zero_near 30 등)·
  C 가치 기본값(recall_led 목표 50 — "기본 목표" 라벨 표기).
- thresholds 신규 키 전부 `diag_*` — SSOT·meta 오버라이드(TUNING 문서).
- 규칙 엔진은 순수 함수(입력: effect/counts/daily — 출력: 문장 배열)
  — LLM 0개·패킷(E)은 defer.
