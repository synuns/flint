# flint v0.7 레퍼런스 조사 (2026-10-23)

기둥 A(적립 자동화)·B(실사용 재개) 조사 결과. 출처 전부 1차 문서.

## B. 실사용 재개 — 10인사이트 (조사 완료)

1. **설정 우선순위는 관례 통일: 플래그 > env > 파일 > 기본값.**
   출처: https://kubernetes.io/docs/concepts/configuration/organize-cluster-access-kubeconfig/
   ("If the `--kubeconfig` flag is set, use only the specified file. Do not merge.")
   적용: `--dsn` 플래그 > `FLINT_DSN` env > 설정파일 > 기본값. 플래그 지정 시 파일
   병합 없이 단독 사용(kubectl 관례).

2. **docker도 동일: `--config`가 `DOCKER_CONFIG` env를 이긴다.**
   출처: https://docs.docker.com/reference/cli/docker/
   적용: env 우선 현구조 유지 — 파일 도입 시에도 `FLINT_DSN` env를 파일보다 위에
   두면 기존 CI·테스트 워크플로가 깨지지 않음.

3. **파일 위치는 `os.UserConfigDir()` 표준으로 충분, viper 불필요.**
   출처: https://pkg.go.dev/os#UserConfigDir · gh:
   https://cli.github.com/manual/gh_help_environment
   적용: `UserConfigDir()/flint/config.json` 한 파일 + 재배치 env
   `FLINT_CONFIG_DIR` 하나만 추가(gh의 `GH_CONFIG_DIR` 모델).

4. **플래그+env 최소 구현: "플래그 기본값을 env로 시드".**
   출처: https://tpaschalis.me/golang-better-cli-cfg/
   적용: `flag.String("dsn", os.Getenv("FLINT_DSN"), ...)` — 의존성 0, 우선순위가
   표준 flag 안에 녹음.

5. **포트 충돌 UX 두 분파: 자동 다음 포트 vs 엄격 실패(strictPort). 고정 DSN
   계약 도구는 엄격 실패.**
   출처: https://vite.dev/config/server-options · 충돌 메시지 사례:
   https://github.com/Prisma/prisma/issues/3591
   적용: 5433은 DSN 계약이라 자동 포트 증폭 부적합 — 즉시 실패하되 점유자와
   대안(포트 변경법 한 줄)을 메시지에 제시.

6. **doctor식 포트 진단은 `docker compose ps --format json`의 Publishers 필드로
   기계 판독.**
   출처: https://docs.docker.com/reference/cli/docker/compose/ps/
   ("Published ports appear in JSON via the `Publishers` field ... Exited
   containers show `"Publishers": null`.")
   적용: doctor가 이 JSON을 파싱해 (a) flint 컨테이너 실행 여부 (b) 5433 매핑
   상태 (c) 타 컨테이너 점유 여부 보고 — lsof 파싱보다 안정적.

7. **통합 테스트 관례 확립: 미설정→t.Skip, 설정됐는데 접속 실패→Fatal.**
   출처: https://konradreiche.com/blog/how-to-separate-integration-tests-in-go ·
   https://storj.dev/blog/go-integration-tests-with-postgres ·
   https://github.com/testcontainers/testcontainers-go/blob/main/testing.go
   적용: `FLINT_DSN == ""` → `t.Skip(...)`, ping 실패 → `t.Fatalf(...)`.
   빌드 태그는 "파일 단위 적용·기본 건너뛰어 리팩터링 오류 숨김" 반론까지
   문서화돀 — 기각.

8. **원커맨드 온보딩: `docker compose up -d --wait --wait-timeout N`.**
   출처: https://docs.docker.com/reference/cli/docker/compose/up/
   적용: `flint setup` = compose up --wait(60s) → 마이그레이션 → 플러그인 설치
   순차. compose 헬스체크가 1차, Go ping 폴링 2차.

9. **폴링 의미론은 pg_isready 체계: 0 정상/1 거부(시작 중)/2 무응답/3 시도 안 함.**
   출처: https://www.postgresql.org/docs/current/app-pg-isready.html
   적용: pgx ping 루프로 동일 의미론 — "거부"는 재시도, "무응답"은 타임아웃
   카운트, 진단 메시지가 "죽었는지 뜨는 중인지" 구별.

10. **이식성 모델: 상태를 단일 디렉터리 + 재배치 env 하나(Dolt `DOLT_ROOT_PATH`
    대칭).**
    출처: https://docs.dolthub.com/docs/sql-reference/version-control/remotes/ ·
    https://www.dolthub.com/blog/2024-12-04-dolt-configuration/
    적용: 설정·플러그인을 `UserConfigDir()/flint/` 단일 트리 + `FLINT_CONFIG_DIR`
    — 머신 이동 = 디렉터리 복사로 종결.

### B 미검증(실행 시 확인)

- `compose up --wait` 구버전 hang 버그(docker/compose#10184) — `--wait-timeout`
  항상 명시로 완화, 실패 경로 실측 필요
- Doltgres 이미지의 기본 compose `healthcheck` 제공 여부(미확인) — 없으면 flint
  compose가 자체 정의

## A. 적립 자동화 — 10인사이트 (조사 완료)

1. **PostCompact 훅이 `compact_summary`를 그대로 준다 — LLM 없이 증류 요약을
   공짜로 획득하는 최적 트리거.**
   출처: https://code.claude.com/docs/en/hooks (공식)
   ("PostCompact hooks receive `trigger` and `compact_summary`. The
   `compact_summary` field contains the conversation summary generated by the
   compact operation.")
   적용: PreCompact 대신 PostCompact가 적립 트리거 본진 — 요약을 `flint write
   --source hook`로 적립만 하면 됨. 추가 LLM 호출 0.

2. **PreCompact는 차단 가능하지만(컨텍스트 한복 복구 시 요청 실패 위험) flint는
   세이프티넷 용도로만.**
   출처: 동일. auto matcher 시 custom_instructions는 항상 null 전제.
   적용: 차단 목적 부적합 — 원문이 곧 잘리는 시점 경고용으로만.

3. **SessionEnd는 1.5초 공유 예산·차단 불가·JSON 출력 전량 폐기 — 무거운 적립
   금지.**
   출처: 동일. ("SessionEnd hooks share a 1.5-second budget")
   적용: SessionEnd는 detached 프로세스로 `flint enqueue`만 하고 즉시 반환.

4. **Stop 훅의 `additionalContext`가 "훅에 LLM 없이 LLM 작업 시키기" 정공법.**
   출처: 동일. ("Stop and SubagentStop also accept
   `hookSpecificOutput.additionalContext`" · `stop_hook_active` · 8연속
   continuation cap)
   적용: 미적립 마커가 있을 때만 "지식 추출 후 flint write --source hook" 넛지.
   `stop_hook_active` + cap 체크로 무한 넛지 방지 필수.

5. **SessionStart source 값에 compact 포함 — 컴팩트 직후가 회수 주입의 두 번째
   기회.**
   출처: 동일 (source: startup|resume|clear|compact|fork).
   적용: PostCompact 적립 실패·넛지 무시 시 다음 SessionStart(compact/resume)에서
   미적립 마커 발견 → 보강 지시 = 이중 안전망.

6. **Letta dreaming 트리거는 "N스텝 완료 후"·"컨텍스트 컴팩트 시" 단 둘.**
   출처: https://docs.letta.com/guides/agents/sleep-time-agents
   적용: flint 자동 적립 트리거도 2개로 족함(Stop 넛지 = 스텝 완료 계열,
   PostCompact = 컴팩트). 자동 적립분은 검토 대기 상태(Letta review-before-applying
   준용).

7. **ChatGPT는 저장 2경로(명시적 요청+자율 판단), 저장은 날짜 스탬프+병합 관리,
   회상은 주입형(RAG 아님).**
   출처: https://embracethered.com/blog/posts/2025/chatgpt-how-does-chat-history-memory-preferences-work
   (시스템 프롬프트 실측 2차 분석 — 부분 검증)
   적용: SessionStart 주입 = 업계 표준(현행 ask 훅과 부합). 자동 적립분 날짜
   스탬프 + "중복은 병합" 원칙.

8. **Zep: 모순 지식은 삭제하지 않고 invalidate — fact 문장 재작성으로 서사 보존.**
   출처: https://www.getzep.com/blog/beyond-static-knowledge-graphs
   ("mark conflicting edges as 'expired' by setting the `expired_at` field")
   적용: dup 대응에 superseded 개념 — 갱신 지식이 오면 구 레코드 invalidate(삭제
   아님). v0.8 수명주기 기둥과 직결.

9. **Mem0 2단계 파이프라인: 후보 추출 → 기존 메모리 대조 후 ADD/UPDATE/DELETE/NOOP.**
   출처: https://arxiv.org/abs/2504.19413
   적용: 추출 후보는 기존 knowledge 검색(중복 감지 재사용) 후 4연산 매핑 — NOOP
   (저장 안 함)와 UPDATE(기존 갱신)가 노이즈 억제 핵심.

10. **세션 훅은 "디스크에만 쓰고 대화에 주입 못 한다"가 설계상 제약 — 마커 파일 +
    다음 세션 회수가 검증된 패턴.**
    출처: https://github.com/affaan-m/everything-claude-code/issues/187 (커뮤니티
    실무 — 1차 아님)
    적용: 아키텍처 확정 — 기록 계열 훅(SessionEnd/PostCompact)은 큐·마커 기록만,
    주입 계열 훅(Stop 넛지·SessionStart)이 회수 담당.
